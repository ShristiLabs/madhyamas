# PostgreSQL High Availability Guide

This document covers PostgreSQL high availability (HA) configurations for
Madhyamas enterprise deployments, including streaming replication, read
replicas, automatic failover, and the read/write split in the Madhyamas
binary.

## Architecture Overview

```
                   ┌─────────────┐
                   │  Madhyamas  │
                   │  (primary)  │
                   └──────┬──────┘
                          │
                    ┌─────┴─────┐
                    │           │
              ┌─────▼─────┐ ┌───▼───────┐
              │  Primary  │ │  Replica  │
              │ PostgreSQL│ │ PostgreSQL│
              │  (writes) │ │  (reads)  │
              └───────────┘ └───────────┘
                    │           │
                    └─────┬─────┘
                     streaming
                    replication
```

## Read/Write Split (Phase 10d.2)

Madhyamas supports routing read queries (`get_traffic`, `get_by_id`, `count`,
`get_capture_stats`, `get_traffic_by_session`) to a read replica and write
queries (`store_request`, `store_response`, `clear_traffic`, `delete_traffic`)
to the primary.

### Configuration

```bash
madhyamas \
  --database-url "postgres://madhyamas:password@primary:5432/madhyamas" \
  --database-read-url "postgres://madhyamas:password@replica:5432/madhyamas"
```

Or via environment variables:

```bash
export MADHYAMAS_DATABASE_URL="postgres://madhyamas:password@primary:5432/madhyamas"
export MADHYAMAS_DATABASE_READ_URL="postgres://madhyamas:password@replica:5432/madhyamas"
madhyamas
```

When `--database-read-url` is omitted, all queries go to the primary
(default behavior, backward compatible).

### Replication Lag

Read replicas may lag behind the primary by a few seconds. This is
acceptable for:
- Traffic list views (analytics, dashboards)
- Historical traffic inspection
- Export operations

It is **not** acceptable for:
- Immediately reading back a just-stored entry (use `get_by_id` on the
  primary — but note that the current implementation routes `get_by_id`
  to the read pool). If you need read-your-writes consistency, omit
  `--database-read-url` or use synchronous replication.

### Synchronous Replication (Read-Your-Writes)

For read-your-writes consistency with replicas, enable synchronous
replication on the primary:

```sql
-- On the primary:
ALTER SYSTEM SET synchronous_standby_names = 'FIRST 1 (replica1)';
SELECT pg_reload_conf();
```

This ensures the primary waits for at least one replica to confirm
receipt of each write before acknowledging the commit. Trade-off: higher
write latency.

## Streaming Replication Setup

### 1. Configure the Primary

```ini
# postgresql.conf (primary)
wal_level = replica
max_wal_senders = 10
max_replication_slots = 10
hot_standby = on
```

```sql
-- Create a replication role on the primary
CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD 'repl_password';
```

```ini
# pg_hba.conf (primary)
host replication replicator 0.0.0.0/0 md5
```

### 2. Initialize the Replica

```bash
# On the replica server:
pg_basebackup -h primary -U replicator -D /var/lib/postgresql/data -Fp -Xs -P -R
```

The `-R` flag creates `standby.signal` and configures `primary_conninfo`
in `postgresql.auto.conf`.

### 3. Configure the Replica

```ini
# postgresql.conf (replica)
hot_standby = on
hot_standby_feedback = on
```

```ini
# postgresql.auto.conf (auto-generated by pg_basebackup -R)
primary_conninfo = 'host=primary port=5432 user=replicator password=repl_password'
```

### 4. Start the Replica

```bash
pg_ctl -D /var/lib/postgresql/data start
```

Verify replication status:
```sql
-- On the primary:
SELECT * FROM pg_stat_replication;

-- On the replica:
SELECT * FROM pg_stat_wal_receiver;
SELECT now() - pg_last_xact_replay_timestamp() AS replication_lag;
```

## Automatic Failover

For production HA, use one of these tools to automate failover:

### Patroni (Recommended)

[Patroni](https://github.com/zalando/patroni) is the most popular
PostgreSQL HA solution. It uses etcd/Consul/ZooKeeper for leader
election and automatic failover.

```yaml
# patroni.yml (example)
scope: madhyamas
name: node1

restapi:
  listen: 0.0.0.0:8008

etcd:
  hosts: etcd1:2379,etcd2:2379,etcd3:2379

bootstrap:
  dcs:
    ttl: 30
    loop_wait: 10
    retry_timeout: 10
    maximum_lag_on_failover: 1048576
    postgresql:
      use_pg_rewind: true
      parameters:
        wal_level: replica
        hot_standby: on
        max_wal_senders: 10
        max_replication_slots: 10

postgresql:
  listen: 0.0.0.0:5432
  data_dir: /var/lib/postgresql/data
  bin_dir: /usr/lib/postgresql/16/bin
  authentication:
    replication:
      username: replicator
      password: repl_password
    superuser:
      username: postgres
      password: super_password
```

### repmgr

[repmgr](https://repmgr.org/) is a simpler alternative that doesn't
require an external DCS (uses PostgreSQL itself for consensus).

### pg_auto_failover

[pg_auto_failover](https://github.com/citusdata/pg_auto_failover) is
Microsoft/Citus's failover solution — simplest to set up for 2-node
(primary + replica) deployments.

## Docker Compose Example (Primary + Replica)

```yaml
version: '3.8'

services:
  pg-primary:
    image: postgres:16
    environment:
      POSTGRES_USER: madhyamas
      POSTGRES_PASSWORD: password
      POSTGRES_DB: madhyamas
    command: >
      postgres
      -c wal_level=replica
      -c max_wal_senders=10
      -c max_replication_slots=10
      -c hot_standby=on
    ports:
      - "5432:5432"
    volumes:
      - pg-primary-data:/var/lib/postgresql/data

  pg-replica:
    image: postgres:16
    environment:
      PGUSER: replicator
      PGPASSWORD: repl_password
    entrypoint: >
      bash -c "
      until pg_basebackup -h pg-primary -U replicator -D /var/lib/postgresql/data -Fp -Xs -P -R; do
        echo 'Waiting for primary...';
        sleep 1s;
      done;
      echo 'Base backup complete, starting replica...';
      docker-entrypoint.sh postgres -c hot_standby=on
      "
    ports:
      - "5433:5432"
    depends_on:
      - pg-primary
    volumes:
      - pg-replica-data:/var/lib/postgresql/data

volumes:
  pg-primary-data:
  pg-replica-data:
```

## Madhyamas with HA PostgreSQL

```bash
# Point Madhyamas at the HA cluster via a virtual IP (keepalived)
# or a load balancer (HAProxy, PgBouncer) that routes to the current primary.
madhyamas \
  --database-url "postgres://madhyamas:password@vip:5432/madhyamas" \
  --database-read-url "postgres://madhyamas:password@replica:5432/madhyamas"
```

For PgBouncer in front of the HA cluster, see [PGBOUNCER.md](PGBOUNCER.md).

## Monitoring Replication

```sql
-- Check replication lag on the primary
SELECT
    client_addr,
    state,
    sent_lsn,
    replay_lsn,
    (sent_lsn - replay_lsn) AS lag_bytes
FROM pg_stat_replication;

-- Check replication status on the replica
SELECT
    status,
    receive_start_lsn,
    written_lsn,
    flushed_lsn
FROM pg_stat_wal_receiver;

-- Check if the replica is in recovery mode
SELECT pg_is_in_recovery();
```

## Partitioning (Phase 10c.1)

For very high-volume deployments (millions of requests/day), consider
weekly table partitioning using `pg_partman`:

```sql
-- Install pg_partman
CREATE EXTENSION pg_partman;

-- Create a partitioned parent table (requires schema migration)
-- See SCHEMA_PARTITIONING_STMTS in the source code for DDL.
-- SELECT partman.create_parent('public.requests', 'timestamp', 'native', 'weekly');
```

Partitioning is **not** enabled by default — it requires a schema migration
(the `requests` table must be recreated as `PARTITION BY RANGE`). See the
source code comments in `crates/madhyamas-core/src/storage/postgres/traffic.rs`
for the partitioning DDL.
